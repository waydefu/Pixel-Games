# Pixel-Games｜雙人異地、零即時溝通協作規則

本流程專為 **A/B 兩個獨立開發端，可能共用同一 GitHub 帳號，彼此不即時聊天**而設計。以 GitHub 作為唯一工作紀錄。目標是可預測的整合，而非增加會議或繁重文書。

## 開發端身分對照（唯一指定來源）

| 執行端 | 固定名稱 | 狀態 |
| --- | --- | --- |
| **A** | **Waydefu** | 已由 Owner 指定 |
| **B** | **cooby19** | 已由 Owner 指定 |

- 建立 Issue、PR 或交接記錄時，**Waydefu 一律填「執行端: A」**。cooby19 一律填「執行端: B」。
- 執行端 A/B 是**專案工作角色**，不是 GitHub 登入帳號、權限或 CODEOWNERS 身分。若兩端共用帳號，也必須在 Issue/PR 自行標明執行端。
- 本表只記錄 Owner 已確認的指派；A＝Waydefu、B＝cooby19。不可僅由提交者名稱或工具模型推斷執行端；異動時以新的 Owner 指定更新本表。

## 1. 開工與認領

1. 先讀 [交接入口](HANDOFF.md)，核對最新 main SHA、[open Issues](https://github.com/waydefu/Pixel-Games/issues)、[open PRs](https://github.com/waydefu/Pixel-Games/pulls) 及 CI；不可用本地或對話記憶取代。
2. 一件獨立工作用 **一個 Issue**；記錄目的、驗收標準、影響模組、相依工作、優先級 P0/P1/P2、執行端 A 或 B。只有指定執行端修改該任務；需要切換時更新 Issue 紀錄。
3. 修緊急故障可用唯一 `HOTFIX-YYYYMMDD-代號` 代替 Issue；hotfix 也要有 PR、驗收及可回退提交，不能當作免管理捷徑。
4. 比對目前 open PR 的修改路徑；若涉及同一核心模組（`main.ts`、`world.ts`、render pipeline、CI、資料格式），先在 Issue/PR 寫出接合與驗證方式，必要時分為依序合併。
5. 從**最新 main** 建個人專用分支；不要在別人的 PR 分支寫入或直接改 main。

### 認領怎麼做、怎麼過期

- 認領＝把 Issue 的「**執行端**」欄位從「未認領」改成自己的 A 或 B（或留言「認領 A」並同步欄位）。PR 的任務 Issue 會被 CI 檢查：必須存在、是仍開啟的 Issue（不是 PR）、執行端與 PR 填的一致；仍是「未認領」會警告。
- **認領會過期**：認領者在該 Issue／分支／PR 上連續 **7 天**沒有留言、提交或 PR 動靜，視為過期。另一端可在 Issue 留言「接手 #N；原認領 X 已逾 7 天無動靜」並改執行端，**前提是沒有該任務的 open PR**；若有 open PR，先在 PR 留言詢問，不直接接手。
- 接手後原認領者的分支與 PR 不得被覆寫；需要其內容時開新分支並在新 PR 的「相依 PR」註明。

### 別人新增的 Issue 怎麼整理

任何人（含另一端、Owner）隨時可能新增 Issue。開工前先整理，不要直接認領第一張看到的：
1. **去重**：搜尋 open／closed Issue 與 PR 的關鍵字與模組；重複的一張保留、另一張以「duplicate」關閉並互相連結。只可關閉**自己建立**的重複 Issue；他人建立的重複項目留言建議，由建立者或 Owner 關閉。
2. **補欄位**：缺優先級、影響模組、驗收條件的，留言補問；未回覆前預設 **P2**，不自行升級別人標的 P0／P1。
3. **拆分**：一張 Issue 含多件獨立工作（會產生多個 PR）時，建議拆分並互相連結，不要一個 PR 吞掉全部。
4. **驗收類 Issue** 與實作類分開：真機、音訊實聽、人工美術驗收記在驗收 Issue，**不得**因為實作 PR 合併就關閉。
   - 新的 NOT RUN 項目**加一列到[驗收總清單 #120](https://github.com/waydefu/Pixel-Games/issues/120)**，PR 的「驗收 Issue」填 #120；不要每個 PR 各開一張。只有需要獨立討論的大項才另開，並掛為 #120 的子 Issue。
   - 反過來，**實作 Issue 在 PR 合併後就關閉**（PR 內文寫 `Closes #N`，或合併後手動關），沒做完的驗收移到 #120，不要讓實作 Issue 為了等真機一直開著。
5. 新 Issue 預設**未認領**；沒有認領前，不要對它開 PR。
6. **標籤手動加**（Issue 範本不會自動帶；表單的 `labels:` 只能是固定值）：每張 Issue 一個優先級 `P0`／`P1`／`P2`，加一個領域 `render`／`gameplay`／`engine`／`governance`／`ci`；驗收類再加 `驗收`。標籤要和內文的優先級一致，不藉由改標籤升降別人的優先級。
7. **審查／盤點報告不逐項開 Issue**：發現留在報告裡並對應到既有 Issue；只為「準備動工」的項目開單，同一個 PR 能做完的小項合成一張。

## 2. PR 契約

每個新 PR 均需填：
- **任務**：Issue #N 或唯一 HOTFIX-ID；同一任務不得被兩個 open PR 同時認領。
- **執行端**：A 或 B；共用 GitHub 帳號也必須填。
- **影響模組**：例如 `render/sky`、`game/input`、`governance`。
- **相依 PR**：無或 #N；未合併依賴需標 BLOCKED，避免半成品先併。
- **交集處理**：若和其他 open PR 共同改核心檔案，具體列出整合方式、順序、回歸測試。未驗證不得填「已完成」。
- **驗收 Issue**：真機／人工驗收尚未做（NOT RUN）時，填追蹤它的 Issue 號碼（可多個）；沒有任何未完成驗收才填「不適用」。這個欄位避免「NOT RUN」在合併後無人追蹤（自 PR #51 起強制）。
- **驗收／回退**：自動測試、人工畫面、真機、音訊實聽分層紀錄；各寫 PASS / FAIL / NOT RUN。

`scripts/check-pr-collaboration.mjs` 會用 GitHub API 比對 open PR：**重複認領同一任務阻擋**；共用檔案預警；共用核心檔案而沒有整合說明則阻擋。對歷史 PR #35/#36 採相容模式，避免新制度無故把舊 PR 變紅。此工具不能辨認同一 GitHub 帳號背後到底是誰，也不能防止尚未開 PR 的私下重複開工，所以 **Issue 人工認領仍必要**。

## 3. 合併條件與交接

- Branch ruleset、必要 CI 和最新 main 合併檢查均通過；**只靠綠燈不等於遊戲好看或手機穩定**。
- 必要檢查「Build, typecheck, unit and browser tests」由 `scripts/check-gate.mjs` 判斷：連續推送時**被新提交取代而取消**的舊執行視為過時、不標紅；任何真失敗、或最新提交上被取消／查不到最新提交，仍然失敗。看到紅燈先確認是不是最新提交的結果。
- 只改 `docs/**` 或根目錄 `*.md` 的 PR 不跑瀏覽器分片；合併後 Pages 在建置通過時就發布，main 上的瀏覽器測試是部署後的監看（細節與前提見 [品質關卡](QUALITY-GATES.md)）。**main 變紅＝線上可能有問題**，優先處理。
- Core overlap 完成整合回歸，且 Owner 對當次 PR 給合併授權；不要自行修改 ruleset 迴避。
- 合併後由 PR 結案關聯 Issue，並記下實際完成與待驗收的差異。若有新已落地功能，同 PR 更新 [功能台帳](FEATURE-STATUS.json)；若有重大決策變更，同 PR 更新 [決策效力表](decisions/DECISION-REGISTER.md)。
- 新端下一次開工以 GitHub 即時狀態接手，不用每天手寫「最新 PR」而形成第二套過時資料。若 CI／Pages／人工驗收沒過，Issue 保留或另外開驗收 Issue。
- 涉及外部素材保留出處與 license；不得復活已淘汰的第二遊戲入口，不可刪失效但有研究價值的紀錄。

## 4. 擴張與平台限制

現有 `Protect main` 強制 PR、必要 CI、不得 force push，但審查批准數為 0，CODEOWNERS 未被強制。**本 PR 不擅改平台權限**。Owner 若要求雙人交叉審查，需要兩個不同的 GitHub 身分，並在 Ruleset 設定 1 位 reviewer／code-owner review；兩個 Agent 共用帳號無法真正形成 GitHub 的獨立審查。詳見 [主分支保護](governance/BRANCH-PROTECTION.md)。

本流程優先監測檔案交集，**不禁止**不同任務在同一檔案並行；是否允許整合由改動的契約和回歸證據決定。

## 5. 節省 AI 額度

A、B 兩端 agent 共同遵守。官方文件沒有寫雲端 session 如何計入額度，因此以下是通用做法與本專案踩過的浪費點，**不是雲端專屬的保證**；不寫具體 token 數字。「啟動時載入多少」由 `AGENTS.md` 的「按需定位」與 [文件索引](INDEX.md) 處理，本節處理 session 中的使用習慣。

1. **一個任務一個 session**：任務結束、對話已很長時換新 session；狀態留在 Issue／PR，不靠對話記憶。舊內容會在之後每一則訊息重複計費。
2. **推送集中成一次**：本機跑完檢查再推；CI 跑完前不重複推送。每次 CI 事件都會喚醒已訂閱的 session（2026-11-08 連續推送造成 3 則被取消的假失敗通知）。
3. **輸出先縮小再讀**：用 `fields`、`per_page`、`tail_lines`，不要整份 CI 日誌或完整的工作流程清單；先找摘要行。
4. **子代理非必要不開**：每個子代理的請求也算額度；要開就用較小的模型。
5. **不設輪詢提醒**：靠 PR／CI 事件喚醒；最多留一個安全網檢查。
6. **截圖要裁切縮小**，只在需要判斷畫面時才看。
7. **工具要有 Issue 才能加**（MCP、外掛、skill）：工具定義也佔 context；不用就停用。來源與停用方式見 [TOOLING](TOOLING.md)。Serena 的淨省量**未量測**（#79）；Ponytail 宣稱的 token 節省是其自己的基準，**未驗證**。
8. **開 session 時選模型與強度**：文件、Issue、監看 CI 這類機械工作用較小的模型與較低強度；設計與除錯再用較強的。
9. **GitHub Actions 分鐘數是另一個額度**：同上集中推送，避免無意義重跑；不用空提交或關閉重開 PR 來觸發 CI。

以上不取代第 1～3 節的認領、PR 契約與合併條件；省額度不得以跳過驗證或測試為手段。
